# 切屏切图网页工具（UV 2D 重映射版）

把你现在这套 **2D UV 重映射** 的切屏流程做成网页：上传一张整幅画面，
浏览器本地按 UV 映射图切出各屏成片，导出 PNG。**一套 UV 集合 = 一个独立单文件网页**，
双击即用、离线、不联网、运行时不依赖 Nuke。

当前已产出：`QiePing_UV2D_LangJiu_1014_ABCD.html`（A/B/D/F 四屏，1.28 MB）。

## 怎么用

双击那个 html（Edge / Chrome 都行，需要 WebGL2）。给画面有三条路：
**拖进虚线框**、点「选择文件…」（虚线框本身也能点）、或直接 **Ctrl+V 粘贴**；
点「生成成片」，几秒后**每屏的成片会直接显示在页面上**（卡片里就是切好的图，
标题栏写着分辨率和文件体积）。点图片或点「放大」可以全屏查看，里面能在
「适应窗口 / 1:1 原始像素」之间切换（1:1 时可用滚轮滚动看细节），Esc 退出。
满意了再逐张下载，或「打包下载 ZIP」一次拿全。

如果某屏生成结果是全黑的，页面会直接提示（多半是素材尺寸超出显卡贴图上限，
把画面缩到 8192 像素以内再传即可）。

> 点「选择文件…」如果没弹选择框，多半是文件被塞在某个软件的预览窗口里打开的
> （那种窗口常常禁用系统文件框）。用系统的 Edge / Chrome 直接打开即可；拖拽和 Ctrl+V 不受影响。

## 原理

这套流程的本质是纯贴图重映射，一个公式：

```
out(x,y) = 素材_双线性_线性空间( u·W − 0.5 , (1−v)·H − 0.5 ) × mask(x,y)
```

* `u,v` 是**归一化坐标**（不是像素）；
* `v` 原点在**左下**（Nuke 惯例）——所以进着色器要写成 `1.0 - uv.y`；
* 插值必须在**线性空间**做（sRGB→linear→插值→乘 mask→linear→sRGB）。

三条都是拿独立的无头 Nuke 探针实测钉死的：用坐标编码图当源时 `STMap` 输出与映射图
R/G 逐点相同；用常量映射图 `(0.5,0.5)` 确认归一化是按**源图尺寸**解释、原点在左下。

## 关键结论：坐标必须 16-bit，8-bit 会糊

同一个 Nuke 工程、同样节点、只换映射来源，实测（`1004/C/001.jpg`）：

| 映射来源 | 平均误差 | p90 | 差异>2 的像素 |
| --- | --- | --- | --- |
| 16-bit 坐标（本工具用的高低位打包） | **0.87 / 255** | 2 | — |
| 8-bit 坐标（`QingPing_UV_*.png`，R=u、G=v、A=mask） | **17.9 / 255** | 51 | 65% |

原因：u 一个 8-bit 台阶 = 1/255 ≈ 0.0039，而屏 A 横向只覆盖 Δu≈0.63，
折算到成片是**每个台阶宽约 41 像素**——画面被切成 41 像素的糊块，换任何算法都救不回来。
所以本工具把坐标拆成「高 8 位 / 低 8 位」两个通道存，浏览器里再拼回 16-bit。

## 流水线

```
UV EXR（32-bit float）
   | ① run_export.ps1  ->  export_uvset.py（在 Nuke 里跑）
   v
sets/<集合>/raw/   u_<屏>.png / v_<屏>.png（16-bit 单通道）、mask_<屏>.png（8-bit）
   | ② pack_uvset.py
   v
sets/<集合>/   gridU/gridV_<屏>.png（1/4 分辨率，高低位打包的 8-bit RGB）+ mask + uvset.json
   | ③ build_page.py
   v
QiePing_UV2D_<集合名>.html   <- 成品，一套集合一个
```

```powershell
$py = 'C:\Users\Admin\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
cd D:\codex\Nuke插件\qieping_uv2d\bake

powershell -ExecutionPolicy Bypass -File run_export.ps1              # ① 导出（约 16 秒）
& $py pack_uvset.py ..\sets\LangJiu_1014_ABCD LangJiu_1014_ABCD 4    # ② 打包（末位=网格倍率）
& $py build_page.py ..\sets\LangJiu_1014_ABCD                        # ③ 出网页
& $py verify_uv2d.py                                                 # ④ 与 Nuke 成片逐像素验收
& $py browser_test.py --mode http                                    # ⑤ 无头浏览器端到端（http）
& $py browser_test.py --mode file                                    # ⑥ 同上，file://（双击的用法）
```

换素材不用重做，只有**换机位/屏体**才需要重跑 ①②③。

## 数据契约

每屏三个文件（`uvset.json` 里登记）：

| 文件 | 内容 |
| --- | --- |
| `gridU_<屏>.png` | 1/4 分辨率，8-bit **RGB**：R=u 高 8 位、G=u 低 8 位、B=0 |
| `gridV_<屏>.png` | 同上，存 v |
| `mask_<屏>.png` | 全分辨率，8-bit 灰度，覆盖率 |

打包公式（**先降采样、再拆高低位**，顺序不能反）：

```
k = round(clamp(u,0,1) x 65535)      R = k >> 8      G = k & 255
```

三条硬约束：

1. **不要把坐标写进 alpha 通道**。浏览器上传带 alpha 的贴图时会把 RGB 按 alpha 预乘掉，
   数据直接毁——所以是 gridU + gridV 两张 RGB，不是一张 RGBA。
2. **先降采样再打包**。反过来等于对高字节和低字节分别平均，进位处会崩。
3. **屏幕数量/名字/分辨率全部由 `uvset.json` 驱动**，代码里没有硬编码 A/B/D/F
   （已用一个只含 A、D 两屏的集合验证过）。

坐标场全画面连续（UV EXR 里屏外也有有效坐标），所以降采样用**普通盒式平均**，
不做覆盖率加权、也不做边缘扩展。**这一点与上一版 3D 烤图相反**（那版的 u/v 是预乘的，
必须反预乘）——两版数据不能混用。

## 验收结果

正式素材 `1004/C/001.jpg`（对照现网 3D 成片 `Out_QiePing/QiePing1004C/`），网格倍率 4：

| 屏 | 平均 | p50 | p90 | 判定（平均≤2 / p90≤6） |
| --- | --- | --- | --- | --- |
| A 6600×1700 | 0.869 | 0.57 | 2.00 | OK |
| B 6600×1580 | 0.926 | 0.62 | 1.92 | OK |
| D 3400×1300 | 0.738 | 0.52 | 1.61 | OK |
| F 3750×750 | 1.530 | 0.86 | 3.45 | OK |

* 8-bit 对照组（只取高 8 位、同一套代码）：**18.1 / 20.7 / 20.0 / 22.8** ——
  高低位打包把误差压掉了约 20 倍；`verify_uv2d.py` 会把这条对比一起打出来当回归保护。
* 无头 Edge 实跑成品网页，`http` 与 `file://` 两种打开方式结果一致：
  **0.881 / 0.941 / 0.738 / 1.543**，与 Python 复算完全吻合。
* 多集合：另建一个只含 A、D 两屏的集合（`Test_AD`），生成第二个 html 并跑通（A 0.881 / D 0.738）。

**一处已知残差**：换一张高频细节很多的画面（`source/1006/water.jpg`，Nuke 现渲对照）时，
A/B/D 是 1.18 / 1.32 / 1.25，但 **F 屏平均 2.19（p90 仍是 5，在 6 以内）**，略高于 2.0 这条自定线。
原因是 F 屏在纵向上把素材**放大**约 1.7 倍，而 Nuke 的 `STMap` 用的是随缩小倍率自动加宽的
Mitchell 滤波，本工具用的是线性空间双线性——这是**滤波核形状**的差异，不是精度问题
（精度问题会是 18~27 那个量级）。

网格倍率是质量与体积的旋钮（`pack_uvset.py` 最后一个参数，实测 `water.jpg` 的 F 屏）：

| 网格倍率 | F 屏平均误差 | 四屏素材 | 成品 html |
| --- | --- | --- | --- |
| 8 | 2.41 | 0.33 MB | 0.46 MB |
| **4（默认）** | **2.17** | **0.95 MB** | **1.28 MB** |
| 2 | 1.74 | 3.22 MB | ~3.7 MB |
| 1（不降采样） | 1.18 | ~22 MB | — |

要更接近 Nuke 就把倍率调小重跑 ②③；正式素材上倍率 4 已经足够。

## 踩过的坑（改代码前先看）

1. **Nuke 的 `-t` 打不开中文路径的 `.py`**（`UnicodeDecodeError`）→ 两个 `.ps1` 都会先拷到
   `D:\codex\_qieping_uv2d\` 再执行；读中文路径的**数据文件**没问题。
2. **Nuke 的 Write 会吃掉路径里的反斜杠**（`D:\a\b.png` → `D:ab.png`）→ 一律正斜杠。
3. **`-t` 不会把额外命令行参数交给 `sys.argv`** → 导出/渲染脚本统一用环境变量收参数。
4. **PIL 与浏览器读 16-bit 多通道 PNG 都会掉成 8-bit**——所以精度只能靠高低位打包，
   验证脚本里也不要用 PIL 去读 16-bit 当基准（我在这上面绕了很久）。
5. **16-bit 坐标不能交给硬件插值**：高低位分开存时 GPU 的亚像素精度误差会被放大 256 倍，
   必须 `texelFetch` 取 4 个格子、拼回 16-bit 之后再插值。
6. **`1.0 - uv.y` 不能漏**：EXR 的 v 原点在左下，贴图的 v=0 是图像第一行（顶部）。
   漏了就是整张图上下颠倒。
7. 应用内预览窗口会禁用系统文件框 → 说明里写清用系统 Edge/Chrome 打开，或改用拖拽/粘贴。

## 假设与边界

* 只处理**单张静帧**；视频/序列不在范围内。
* 输出 8-bit sRGB PNG、黑底，尺寸严格等于该屏 UV 图的分辨率。
* 输入整幅拉伸到画面坐标系（与 Nuke 里 Root/Read 强制 `6000 1538` 一致），
  宽高比不是 3.901 时页面会提示。
* 全程只读 W 盘上的工程、UV、素材与成片，不修改任何现网文件。
